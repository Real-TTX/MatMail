# CLAUDE.md

Guidance for working in this repository. Keep it in sync with the code: update it whenever architecture, persistence, interfaces or major data flow change.

## What MatMail is

A small self-hosted mail **gateway with a built-in web mail client** (think "tiny Exchange"). Mail accounts of external providers (Strato, Netcup, …) are connected once; users then work with the gateway's own credentials in the web client, in Outlook/Thunderbird (IMAP + SMTP of the gateway) or send through it as a smart host. A hoster can give customers their own **tenant**; the provider's real credentials never leave the server, and a provider move only changes one record.

Stack: ASP.NET Core on **.NET 10**, C#, **Razor Pages** (no Blazor/SPA framework) + TagHelper controls on the design toolkit **MatUi** (the toolkit of the Mat apps, see *The look (MatUi)* below), EF Core + **PostgreSQL**, MailKit/MimeKit, Docker-first. Web port **9933**.

## Build / run / test

- **Build:** `dotnet build MatMail.slnx` (note: `.slnx`). SDK 10 (see `global.json`). The build is expected to end with 0 warnings.
- **Run / test the app: always rebuild the container and redeploy the stack** (project rule): `./scripts/redeploy.ps1` (`-Fresh` also wipes the volumes → the setup page appears again). Dev stack: `docker-compose.dev.yml` → http://localhost:9933, plain HTTP; mail on host ports 2525/2587/2465/2143/2993; PostgreSQL on 15432.
- **Release stack:** `docker-compose.yml` (image `ghcr.io/real-ttx/matmail`), plain HTTP on 9933 (made to run behind a reverse proxy that terminates TLS; `Server.WebHttps` is off by default, the mail servers use the certificate anyway), standard mail ports. As simple as it gets and the same file as in the README: no variables for the app (the variables of the Mat platform, `MAT_API_KEY` and `MATIDENTITY_*`, stand there as comments only), no health check, no `sysctls`, one volume for `/data` and one for PostgreSQL (its `POSTGRES_PASSWORD` equals the default of `MATMAIL__Database__Password`). That works because the app waits for PostgreSQL and creates its database itself (`StartupInitializer`); keep it that way, do not grow the file.
- **Unit/integration tests:** `dotnet test MatMail.slnx`. Tests that need PostgreSQL read `MATMAIL_TEST_DB` (an admin connection string, e.g. `Host=localhost;Port=15432;Database=postgres;Username=postgres;Password=matmail`, with the dev stack up; every test class creates and drops its own database) and are skipped without it. Tests of the SMB backup targets read `MATMAIL_TEST_SMB` (`localhost;share=backups;user=backup;password=backup-secret`, a Samba container – see `tests/MatMail.Tests/Support/TestSmb.cs`; SMBLibrary only speaks to port 445, so on Windows run the suite in a Linux container next to Samba; the CI starts one). Tests against a real provider read `MATMAIL_TEST_IMAP` (`localhost:31143;pop3=localhost:31110;smtp=localhost:31025;api=localhost:31080`, a GreenMail container – see `tests/MatMail.Tests/Support/TestProvider.cs`; the CI starts one). A shortened value silently points the REST API at the wrong port and fails the provider tests. Tests against a real LDAP server read `MATMAIL_TEST_LDAP` (`localhost:10389;ldaps=10636`, the image `rroemhild/test-openldap` with the Planet Express staff – see `tests/MatMail.Tests/Support/TestLdap.cs`; the CI starts it; locally `docker run -d --name ci-ldap --network container:ci-holder rroemhild/test-openldap`). `localhost` is deliberate: in a Linux container it is `::1` first, which the server does not serve, and that is what `DirectoryConnectTests` and the real-server tests guard. Tests against a real **Active Directory** read `MATMAIL_TEST_AD` (`localhost:1389;ldaps=1636`, a Samba domain controller, image `nowsci/samba-domain`, privileged, a minute to provision; **not in the CI**, the recipe with the `samba-tool` commands is in `tests/MatMail.Tests/Support/TestAd.cs`; from a Linux container use `host.docker.internal:1389`): `sAMAccountName`, `userPrincipalName`, `userAccountControl`, the nested-group rule, `objectGUID`, referrals, the codes of a failed bind (`data 52e`, `data 533`).
- **Migrations:** `dotnet ef migrations add <Name> --project src/MatMail/MatMail.csproj --output-dir Migrations` (local tool, `dotnet tool restore`). They are applied automatically at start-up. A new `bool` column needs `HasDefaultValue(…)` in the model, otherwise EF adds it with `false` for existing rows. **A restore applies migrations too** (over restored data, inside one transaction, through `IMigrator`): custom `migrationBuilder.Sql(…)` must work on a database that has rows, and **never use `suppressTransaction: true`** (EF refuses such a migration inside the restore's transaction, so no older backup could be restored any more). A new migration is covered by `BackupRestoreTests` (it restores a backup of every earlier schema version).
- **Backup from the command line:** `dotnet MatMail.dll --backup <file or folder> [--passphrase-env VAR]` (a complete backup of a running or stopped installation; the passphrase comes from an environment variable, never from an argument), `--restore <file> [--passphrase-env VAR] [--force] [--no-safety-backup] [--keep-queue]` for a *stopped* installation (refuses while other sessions use the database, unless `--force`). `MATMAIL_RESTORE_FROM=<file>` (+ `MATMAIL_RESTORE_PASSPHRASE`) restores into a still empty installation at start-up – a new server with the data of the old one; once there is data it does nothing.
- **The toolkit:** `scripts/update-matui.ps1` copies the files of MatUi from the running MatDesign (`http://localhost:8060/ui/matui.zip`) into `src/MatMail/wwwroot/matui/` (copy, never link: the app works offline); `node scripts/build-icons.mjs` rebuilds `matmail-icons.svg` (the icons of the library of MatDesign that MatMail uses, names in `scripts/icons-extra.json`). `ToolkitTests` checks what could be broken without seeing it: every icon in a page, a control, a script or a menu exists in a sprite, no page has an inline style, script or handler, no script opens a dialog of the browser, the style sheets of the app have no literal colour, every menu item leads to a page, the accent of the app is the one in `matui.css`. A new toolkit release is copied in, the tests run, the pages are looked at in light, dark and at 390 px.
- **Translations:** UI text is English in the source (`L["…"]`), German in `src/MatMail/Resources/SharedResource.de.resx` (English text = key). `node tools/i18n.mjs check` lists missing keys (and keys that differ only in case: the resource compiler ignores the second one with a warning), `add patch.json` merges `{ "English": "Deutsch" }`, `prune` drops unused ones. Keep it complete before committing UI changes. English is the default language.
- **Screenshots** for the README: Playwright + Edge headless against a demo instance (the embedded browser pane does not render frames here); pictures live in `docs/images/`, demo data only. 1360 px wide at device scale factor 2 (mail pictures 860 px high, administration and account pages 1000 px so that the whole navigation fits, phone 390×844). The README follows the layout of MatFile's: logo and tagline, a hero picture, *What this is about*, *At a glance*, one section with a short caption per picture or row of pictures, then quick start, status, development.

## Rules from the project brief (do not drift)

- **Git:** branches `main` (release) and `dev` (development); work on `dev`. Commit under the user's own name. **Never add Claude/Anthropic as author or co-author** (no `Co-Authored-By`, no "Generated with" line). Do not push unless asked.
- **Versioning** (`Directory.Build.props`, channels): release `<major>.<minor>.<build>-<date>` (main), nightly `nightly-<build>-<date>` (dev), local `local-<date>`. The CI (`.github/workflows/docker.yml`) builds, tests and pushes the image to GHCR.
- **UI:** CRUD = list page + separate edit/create page. Every list has the **toolbar above** (search, filters, sort), list actions **below, left aligned** (destructive ones with distance), **pagination directly under the table** and nothing else. Form buttons in one row, positive → negative: `Save`, `Back`, spacer, `Delete`. Icons where they help. **One code base per control** (`src/MatMail/Controls`): list, table, pagination, toolbar, form, field (incl. the rich text editor), tabs, dialog, picker, buttons, alert, card, meter; several of the same control may share a page. **Mobile first-class:** dialogs and custom dropdowns become full-screen sheets on phones. The mail client looks like a modern client (Gmail). Dependent form fields are shown only when needed (`show-when-field`). **Everything is built from the toolkit** (rulebook of MatDesign, `http://localhost:8060/rules`): classes `mat-*`, tokens `--mat-*` only (no literal colour), no inline style, script or handler, no `window.confirm/alert/prompt` (dialogs of the toolkit: `data-confirm`, `MatUi.confirm/prompt/alert`, toasts), every `td` has `data-label` (`mm-table` does it), icons from the sprites. What only MatMail has carries a prefix: `mm-*` (shell, pages, editor) and `mail-*`/`compose-*`/`reader-*` (the web client).
- **Code:** little nesting, several related business functions may live in one class, readable names (Microsoft C# guidelines). No repository layers.
- **Database:** PostgreSQL for logic and mail, JSON (`/data/config/app.json`) for configuration. Tables are **PascalCase** (singular, = entity name), primary key always **`Id` BIGINT**, every row has `CreateDate`, `CreateUserId`, `UpdateDate`, `UpdateUserId` (filled by `MatMailDbContext.SaveChanges`). Tables whose key acts as a security token carry a `Token` (e.g. `UserSession`: `Id` + `Token` uuid). **Everything persistent lives in PostgreSQL or under `/data` – nowhere else** (a backup is exactly those two; see *Backup, restore and versions*).
- **Sessions** are rows in `UserSession` (cookie carries only the token) → they survive container restarts; data-protection keys live in `/data/keys`.

## Architecture in short

Single web project `src/MatMail` (+ `tests/MatMail.Tests`).

- `Data/` – entities (`Entities/*.cs`), enums (stored as text), `MatMailDbContext` (audit columns, tenant guard, **global tenant query filter** driven by `CurrentUser.TenantId`; use `IgnoreQueryFilters()` deliberately), migrations.
- `Services/` – accounts and the application around them: `SignInService` (credentials, sessions, claims, throttling), `SessionCookieEvents` + `SessionCache` (the cookie is validated against the DB, 15 s cache), `CurrentUser` (web principal or an explicit actor for background/IMAP/SMTP: `RunAs…`), `TwoFactorService` / `TwoFactorPolicy` / `AppPasswordService` / `TwoFactorTicket` / `TwoFactorSetupMiddleware` / `Totp` (second factor, see below), `TenantService`, `UserService`, `MailboxService`, `Permissions` (role catalogue), `BrandingService`, `ThemeService` + `Fmt` (look and time zone of the user), `CertificateProvider` (PFX/PEM/self-signed, hot reload), `ProviderConnector`, `SecretProtector`, `ActivityLogger` (the operational log) and `TransferLog` (the mail transfer log, see below).
- `Push/` – notifications (Web Push): `PushKeys` (the server's VAPID key pair, made on first use in `config/push-keys.json`), `WebPushEncryption` (RFC 8291, tested byte for byte against the RFC's example), `WebPushClient` (`IPushSender`: signs and posts; only connects to public addresses), `PushPlanner` (who is told what: owner of the mailbox, others who may read it when the device asked for that; unread mail in inboxes; several at once = one notification), `PushNotifier` (hosted service: listens to `MailEventHub`, collects for two seconds, sends, keeps `PushSubscription` rows clean), `PushService` (devices of a user). Tests: `FakePushSender` stands in for the push services (`PushDatabaseTests`); the encryption is checked against the RFC's example (`WebPushEncryptionTests`).
- `Backup/` – backup and restore, see *Backup, restore and versions* below: `BackupWriter` (archive), `BackupArchive` (open, verify), `BackupRestorer`, `BackupEncryption`, `BackupJob` (a backup *file*), `RestoreStartup` (+ `PendingRestore`, `RestoreProgressHost`: restore at start-up, command line), and the scheduled part: `BackupService` (runs a plan), `BackupScheduler` (hosted service), `BackupCoordinator` (one backup at a time, progress), `BackupStorage`/`SmbBackupStorage` (targets), `BackupPolicies` (retention, schedule), `BackupOperations` (download a backup, prepare a restore). `Versioning/` – `SystemSettings` (rows of `SystemSetting`), `DataMigrations` (steps for what is not schema), `VersionGuard` (newer data is never touched).
- `Directories/` – Active Directory / LDAP, see *Directories* below: `DirectoryService` (what a directory is asked: find a login, may they sign in, is this their password, who is there; the **mapper** turns entries into `DirectoryUser`s), `LdapDirectoryClient` + `LdapDirectoryClientFactory` (Novell.Directory.Ldap, behind `IDirectoryClientFactory` so that tests use `FakeDirectory`), `LdapFilter` (RFC 4515 escaping), `DirectoryProvisioner` (users of a directory: sign-in of somebody new, `VerifyAsync` for an existing one, import, link, comparison), `DirectoryPasswordCache`, `DirectoryAttemptLimiter`, `DirectorySyncService` (hosted: the comparison every `Directories.SyncMinutes`).
- `MailSync/` – pulls mail from the provider accounts (IMAP incl. IDLE/flag sync, POP3), routes it through `MailDelivery`, keeps or deletes on the server per account; `LiveAccess` serves bodies that stay on the provider; `UserSyncService` is "Synchronise now" for ordinary users (see below).
- `MailServer/Imap`, `MailServer/Smtp` – the gateway's own servers (hand-written IMAP4rev1 on 143/993 and SMTP: relay 25, submission 587, implicit TLS 465). Sign-in per address or login name, throttled per (client, login); sessions re-check the user. `MailServer/Outbound` – the outgoing queue worker (provider account or direct delivery with MX lookup, retries, bounces).
- `Messaging/` – the core: `MailStore` (raw message + parsed metadata, folders), `FolderService` (the folder tree), `MailboxUsageService` (storage per mailbox and folder), `MailboxQuotaService` (the storage limit: *full* → `MailboxFullException`), `MailDelivery` (recipient → mailbox, catch-all, *Unassigned*; runs the mailbox rules and writes the transfer log), `MailRuleEngine` (mailbox rules, forwarding), `MailSubmission` (everything that leaves: **template → server signature → footers**, then local delivery or the queue), `SendRouting`, `RelayPolicy` (smart-host rules), `SignatureService`, `TemplateService`, `InlinePictures` (data: pictures become `cid:` parts), `MessageContent` (signed/encrypted mail is never changed), `MailBodyRenderer` (sanitised HTML document for the reader), `ComposeService`, `MailAccessService` (own and delegated mailboxes), `MailQuery` (the search language, see below), `MailListService` (the lists of the web client: a folder or a search page by page, the ids for "select all that match", the thread of a message), `MailEventHub` (push to the web client).
- `Api/MailApi.cs` – JSON API of the web client (`/api/mail/...`). The client is plain JS: `wwwroot/js/mail-core.js`, `mail-ui.js`, `mail-compose.js`, `mail-viewer.js`, `mail-search.js` (the advanced search: a dialog of the toolkit behind the options button of the search field in the top bar). `GET /messages/ids` lists all ids a list request matches (at most `MailApi.MaxBulk`, newest first) for the bulk actions of "select all that match". `MailApi` does not touch the `DbContext`: what it needs from the database is a method of a service (`MailStore.FindAsync`, `MailListService`, `FolderService.GetKindAsync`, …), so keep it that way.

Two-factor authentication still applies: a user with a second factor gets the ticket (Lax, carrying the ID token) and `/Account/TwoFactor` (`MailIdentityUsers.SendToSecondStep` wraps MatPlatform's `OnTicketReceived`). The login page challenges MatIdentity unless `?local=1`, `?signedOut=1`, `?ssoError=1`. IMAP/SMTP never see any of it. `SetupRedirectMiddleware` lets the platform paths through; the container health check (`--healthcheck`) asks `/api/health` (the restore host answers it as `degraded`). Tests: `PlatformDefinitionTests` (definition, validator, setup redirect; no database), `PlatformWebTests` (endpoints and sign-in, the whole app in memory through `Support/PlatformFactory.cs`, `MATMAIL_TEST_DB`, a collection that runs alone), `ExternalSignInTests`.
- `Configuration/AppConfig.cs` – JSON config + `MATMAIL__Section__Key` environment overrides (sections Database, Display, Server, Tls, Smtp, Imap, Sync, Queue, Push, Backup, Directories, Retention).
- `Controls/` – the TagHelpers (`mm-…`; each renders toolkit markup: `ListTagHelper`, `TableTagHelper`, `PaginationTagHelper`, `ToolbarTagHelper`, `FormTagHelper`, `FieldTagHelper`, `PickerTagHelper`, `TabControls`, `DialogControls`, `ButtonControls`, `ContentControls` = alert, card, meter), `Toolkit` (reads both icon sprites, `IconMarkup`, the texts of the toolkit script in the language of the page: `LanguageAttributes`), `NavModel` (menu items, groups, badges: a count above 99 reads `99+`) and `ShellModels`. `mm-field kind="richtext"` is the rich text editor (`wwwroot/js/rte.js` starts itself on `textarea[data-rich-text]`).

Never edit a PNG by hand; `AppIconTests` guards the sizes and the names that pages, manifest and service worker use. Background and M are the accent of the app (graphite #475569), the seal and the stamp are warm (amber, pink) on purpose so that they stand out on the gray and are never blue; a new accent means new masters. A user belongs to one tenant; addresses are unique across the server, so mail between tenants is local mail (delivery runs as the system).

## Things that are easy to get wrong

- **Backup, restore and versions** (`Backup/`, `Versioning/`). *What a backup is:* one zip file (`manifest.json` last; `db/<table>.<n>.copy` = PostgreSQL binary `COPY` of **every table of schema `public`**, read in one `REPEATABLE READ` snapshot, cut into parts of 512 MiB; `data/<path>` = **every file under `/data`** except `tmp`, `backups`, `restore`), optionally encrypted as a whole (`BackupEncryption`: AES-256-GCM in 1 MiB chunks, key from the passphrase with PBKDF2-SHA256, every chunk authenticated with its number and a last-flag, random access so no decrypted copy is needed). The manifest holds sizes and SHA-256 of every part, the migration history, the data version, sequence values; every part is checked while it is read. Nothing is listed by hand: a **new table or file is part of the backup without a change**. Hence the rule: **never keep state anywhere but PostgreSQL or `/data`** (not in `/tmp`, not in the image, not in a second volume); anything that must not be backed up goes to `/data/tmp`. *Three version numbers* make old backups restorable: the **schema** (EF migrations; the backup carries the last one), the **layout of the files and of data that a migration cannot express** (`DataMigrations`, stored in `SystemSetting` "DataVersion" and in the manifest; the first release is 1; a change gets the next number and a step in `DataMigrations.All` that brings the old layout to the new one – numbered without gaps, checked), and the **backup format** (`BackupFormat.Version`; a program reads every format up to its own). A program never touches data of a newer version (`VersionGuard`: at start-up the database must not have migrations this program lacks, the data version must not be newer; a backup of a newer version is refused). *Restore* (`BackupRestorer`, one database transaction): files are laid out and checked in a scratch folder first; then `DROP SCHEMA public CASCADE`, EF applies the migrations up to the **backup's** version (through `IMigrator` on the restore's connection and transaction; the history table is created first, because EF reads it and takes a failed read as "none yet", which would abort the transaction), tables are truncated (seed rows of migrations), foreign keys are dropped, the tables are loaded by `COPY` (row counts checked), the keys come back (and are validated), sequences continue, EF applies the **remaining** migrations over the loaded data (= a normal upgrade), `DataMigrations` run over the staged files and the database, versions are noted, fix-ups run, the files replace the top-level entries of the data volume that the backup holds (the old ones are moved aside and put back if the commit fails), commit. Any error = rollback, nothing changed. Fix-ups (`FixUpAsync`): `MailFolder.UidValidity` is raised (IMAP clients reload folders; the restored state may be older than what they know), queued outgoing mail is put on *failed* with a note (it may have been sent since the backup; the administrator retries what is missing). `config/app.json` comes from the backup **except the sections `Database` and `Server`** (how this machine is deployed: a restore must never make it unreachable). *Who runs it:* a running program does **not** restore itself: the web interface writes `restore/pending.json` (`PendingRestore`; the passphrase protected with the key ring, which is still the old one then) and stops the process; Docker's restart policy starts it again and `RestoreStartup` (called first thing in `Program.cs`) restores while `RestoreProgressHost` (a tiny web server on the same port, `/healthz` answers "restoring") shows a progress page, takes a safety backup of the current state first (`backups/matmail-pre-restore-…`, same passphrase, last three kept; if it cannot be made the restore stops) and writes `restore/result.json` (`RestoreReport`) for the backup page. *Plans, targets, runs* (entities `BackupTarget`/`BackupPlan`/`BackupRun`, installation-wide, they travel with every backup): a **target** is a folder of the server (`LocalTargetPolicy`: outside `/data`, or inside `/data/backups`; anywhere else in the volume would put backups into the next backup) or a folder on an **SMB share** (`SmbBackupStorage`, SMBLibrary, SMB 2.0.2 to 3.0.2 on port 445 only (never 3.1.1: a server that requires it is refused), signs and encrypts (AES-128-CCM) when the server or the share demands it – tried against Samba with `server signing = mandatory` and `server smb encrypt = required`, global and per share –, a connection per operation, uploads go to `<name>.partial` and are renamed when complete and of the size of the local file; password stored with `SecretProtector`). A **plan** names target, schedule (hourly every N h / daily / weekly / monthly, in the time zone of the installation: `BackupSchedule.NextRunUtc`, handles the DST gap and the doubled hour), retention (`KeepLast` + newest of each of the last `KeepDaily` days / `KeepWeekly` weeks (Monday to Sunday) / `KeepMonthly` months, a backup stays when any rule keeps it, the newest always stays: `BackupRetention`), optional encryption (passphrase kept protected on the server so scheduled backups can be encrypted – the administrator must keep a copy elsewhere: it is also inside every backup) and verification. A **run** is written when it is over (success or failure; nothing is stored while it runs – progress is in memory, `BackupCoordinator.Current`). File names (`BackupFiles.Name`): `matmail-<first 6 of the installation id>-<p<plan id>|manual|pre-restore>-<UTC yyyyMMdd-HHmmss>-<version>.zip|.mmbak`; retention **only touches files of its own plan *and* installation** (several installations may share a NAS folder), never anything else. `BackupScheduler` looks every 30 s: plans with `NextRunDate <= now` run one after the other (also what came due while the program was off); a plan without a next time gets one and does not run at once; a failed scheduled run is tried again after 30 minutes up to `BackupService.MaxRetries` times, then waits for its next regular time; the administrators (system administrators with a mailbox) get a message in their gateway mailbox at the first failure and when it is given up; a manual run does not move `NextRunDate`. Only one backup (or a restore preparation, or a download) runs at a time. `Backup.Enabled` / `Backup.TempDirectory` (`MATMAIL__Backup__…`): the scratch folder needs room for the backup (twice when encrypted); default `{data}/tmp`. `AppConfig.DataDir` is the data volume (not part of the file).
*The pages* (`Pages/Admin/Backup/*`, system administrators only, one convention line in `Program.cs`): `Index` (what runs now, the report of the last restore from `restore/result.json`, warnings, history, "Back up now"), `Plans`/`Plan`, `Targets`/`Target` (test connection, list of shares; a saved target is checked at once), `Restore` (backups of a target, download of one, upload), `RestoreConfirm` (what the backup holds, passphrase, options, then `RestorePreparation`), `Download` (`BackupDownloads`: made in scratch space, offered for an hour). `wwwroot/js/backup.js` polls `?handler=Status` (`BackupStatus.Json`: `activity`, `preparation`, `download`; states as strings), uploads with XHR and waits for the restart (`/healthz` says "restoring" while the progress page of `RestoreProgressHost` is up). **An upload is the raw body of the request** (`Restore?handler=Upload`, `Account/Setup?handler=Upload`; `[DisableRequestSizeLimit]`, CSRF through the `X-CSRF-TOKEN` header): a form would be copied to a temporary file first, and a backup is gigabytes. The setup page offers the same restore while there are no users (the setup middleware lets that one path through).
*When you change persistence:* a new table/column = a normal migration; a new kind of file or a change of a file's format = a `DataMigrations` step; run `BackupRestoreTests` (they restore a backup of every earlier schema version, check every table and file after a round trip, damaged and encrypted backups, and that a failed restore changes nothing) and `GoldenBackupTests` (two real backup files of the first version, `tests/MatMail.Tests/Fixtures/Backups/backup-format-1.zip|.mmbak`, with rows in every table: restored into a fresh database, checked for rows, files, sign-in and an attachment byte for byte – the only proof that what an *old* program wrote still restores, because every other test writes its backups with the current code; **never make these files again**, a new `BackupFormat.Version` adds a second pair next to them). **Never delete, rename or change a migration that a release contained, a squash included:** a backup is restored by building *its* schema with the migrations up to its version and migrating forward, so a missing or altered one makes every older backup "newer than this version" or unreadable. `FixUpAsync` names tables and columns, so a rename of `MailFolder.UidValidity` or `OutboundMessage.Status` shows there.
- **Signatures, footers and templates** are HTML with `{{Placeholders}}` (`SignatureContext`); the HTML is cleaned when saved (`SignatureService.SanitizeTemplate`, placeholders survive in attributes) and again when rendered. A line whose placeholders are all empty is dropped. `Signature.AddOnServer` appends a signature to messages of mail programs/smart hosts that carry none; footers go on every message. "Carries one" is decided by `SignatureDetector`: the markers of the programs (`mm-signature`, `moz-signature`, `gmail_signature`, id `Signature`, `_rc_sig`, Evolution's), the `-- ` separator (HTML and plain text, a short block, not quoted), the text of ours; only what the sender wrote counts (block quotes, `gmail_quote`, everything below Outlook's `divRplyFwdMsg`/`appendonsend`/header line, and in plain text below a banner or a From/Sent header), a tagline of a phone ("Sent from my iPhone", "Get Outlook for iOS") is no signature, and one signed version of the text keeps the signature off both (`SignatureDetectorTests`). `MailTemplate` puts a message into an HTML frame (`{{Body}}`), chosen by scope, source (`SubmissionSource`: web, mail program, smart host) and optionally a smart-host rule.

- **Search** (`MailQuery`): the text becomes a tree (`AndNode`/`OrNode`/`NotNode`/`TermNode`) and from that an EF expression, no fulltext engine. Operators `from to subject has:attachment is:unread|read|starred|answered|draft in before after older_than newer_than larger smaller` and their German names (`von an betreff hat ist ordner vor nach älter_als neuer_als größer kleiner`), `OR`/`ODER`/`|` (binds weaker than the blank between terms: `a OR b c` is `a OR (b c)`; brackets make it explicit), `-`, `( )`, `{a b}` (either), `key:(a OR b)`, quoted phrases. - **Directories** (`Directories/`, `Pages/Admin/Directories/*`, permission `directories.manage`; entity `DirectoryConnection`, columns `User.DirectoryId|DirectoryDn|DirectoryUid|DirectoryDisabledDate`). A directory belongs to a tenant: server, encryption (none / STARTTLS / LDAPS), the account that searches, base, filter, login attribute, the **mapper** (attribute → name, address, first and last name, title, phone, mobile, department; empty = not filled from the directory), a group that says who may sign in (read from the person's `memberOf` – Active Directory's nested rule `1.2.840.113556.1.4.1941` on request – or from the member list of the group) and what a first-time user gets (roles, a mailbox). *The password of a person is never stored and never read:* `VerifyPasswordAsync` binds **as the person on a connection of its own**; **an empty password is never sent** (a bind without a password is an anonymous bind that many servers answer with success – `LdapDirectoryClientFactory.CheckPasswordAsync` and `DirectoryService.VerifyPasswordAsync` both refuse it, and the tests say so). **Every value that goes into a filter is escaped with `LdapFilter.Escape`** (a login is typed by whoever sits in front of the web client). *Where it hooks in:* `SignInService.ValidateCredentialsAsync` asks `DirectoryProvisioner.SignInNewAsync` for a login that is no user here yet (made on success, the password is checked right there) and `VerifyPasswordAsync` (private) for a user with `DirectoryId` – **any new way to sign a user in has to go through that, never `_hasher` directly**; `CanSignInAsync` includes `DirectoryDisabledDate is null`. A user made from a directory has a random hash nobody knows; `UserService.UpdateAsync`/`ChangePasswordAsync` refuse passwords for such users and `/Account/Password` shows a notice instead of the form. IMAP and SMTP remember a success for two minutes (`DirectoryPasswordCache`, a keyed hash, web never); wrong passwords for somebody with no user yet are counted per login (five in 15 minutes) and per client (50) by `DirectoryAttemptLimiter` – **the lockout of the directory counts every failed bind**, so MatMail must not be the way to lock people out of their company accounts; somebody with a user is held by that user's lockout. The comparison (`SyncAsync`, every hour and on demand) sets `DirectoryDisabledDate` for people who are gone, disabled (`userAccountControl` bit 2) or outside the group, ends their sessions (`SessionCache.InvalidateUser`) and clears it when they are back; a directory that cannot be reached changes nothing (`LastSyncOk = false`). A login that a user has here already always belongs to that user (login names are unique across the server); `LinkAsync` switches a local user over on purpose (import page), a deleted directory leaves its users with `DirectoryId` null (FK `SET NULL`) and nobody can sign in as them until an administrator gives them a password. *Library traps:* Novell connects to the **first** address of a name and has no second try – `LdapDirectoryClient.ConnectAsync` filters to one address at a time (`ConfigureIpAddressFilter`) and moves on when a connect is refused (with `localhost` and IPv6 first the plain library says "Connect Error"); it says "Connect Error" for everything, so `Reason` reads the innermost exception; its `RemoteCertificateValidationCallback` for TLS is the one of `System.Net.Security`. The namespace is `MatMail.Directories`, never `…Directory` (it would shadow `System.IO.Directory`). Tests: `FakeDirectory` (a directory in memory with the small part of the filter language MatMail uses, splitting on a raw `*` *before* unescaping), `DirectoryProvisioningTests`, `DirectoryLdapTests` (`[LdapFact]`, `[LdapDbFact]`), `DirectoryAdTests` (`[AdFact]`, `[AdDbFact]`, local only), `DirectoryConnectTests` (sockets only), `DirectoryAttemptLimiterTests`.
- **Two-factor authentication** (TOTP, RFC 6238, no library; QR code drawn on the server by QRCoder). Web sign-in: password → `SignInService.ValidateCredentialsAsync` returns `SecondFactorPending` → the Login page issues the `MatMail.TwoFactor` ticket cookie (data-protected, 5 minutes, HttpOnly, SameSite Strict, path `/Account`; not a session) → `/Account/TwoFactor` → only then the session. **Nothing but the Login and TwoFactor pages decides that the second step happened** (`SignInAsync` does not check): any new way to create a session has to enforce it. Wrong codes count against the same atomic lockout as wrong passwords; a code works once (`UserTotp.LastUsedStep`). IMAP and SMTP cannot ask for a code: `SignInPurpose.Protocol` accepts **app passwords** (24 characters, PBKDF2, shown once, `AppPassword`), and the account password only while 2FA is neither on nor required; app passwords never work on the web. The tenant policy (`Tenant.TwoFactorMode`: optional, administrators, everyone) and the role flag (`Role.RequiresTwoFactor`) make it mandatory; someone bound to it but not enrolled is held on `/Account/Security` by `TwoFactorSetupMiddleware` (a fixed list of open addresses, `/api` answers 403). Permission `security.manage`. Lost phone and no recovery codes: an administrator resets it (user page), or `DELETE FROM "UserTotp" WHERE "UserId" = …` (cascades to the recovery codes). Test helpers: `TestClock`, `TwoFactorTestSupport`.
- **Mailbox rules** (`MailRule` with `MailRuleCondition` and `MailRuleAction`; pages `/Account/Rules` and `Rules/Edit`, script `rules.js`). The engine decides **before the message is stored** (`MailDelivery.StoreAsync`): the message arrives read, starred, labelled and in its folder, so nothing flickers through the inbox and no notification is sent for it. Rules run only for mail that is routed into an inbox: not for the *Unassigned* bucket, not for backup/migration copies, not for `DeliverToMailboxAsync`. A problem of a rule never costs the message (the delivery logs it and stores without rules). Conditions on what is not there (the text of a live-access stand-in, a missing header) never match, not even negative ones; a rule without conditions or with an empty text matches nothing. **Forwarding is a redirect**: the original bytes with `Resent-*` headers in front and, as envelope sender, an address of the mailbox (the provider accepts that), through `MailDelivery` (local) or the outgoing queue. It happens **after** the copy is stored, so a loop of forwarding rules meets its own copy (Message-ID de-duplication) and ends; `X-MatMail-Forward-Hops` (limit 5) is the second guard. A message a rule changed on arrival gets its `UpdateDate` bumped after the provider record is written (`ImportResult.RuleChangedFlags`), otherwise the flag comparison would take the provider's flags and undo the rule; a rule that deletes a message counts as "dealt with" for *delete after download*. Deleting a folder a rule moves into keeps the action with `FolderId = null` (it then does nothing). Only people with **Manage** access to a mailbox (the owner, or delegated) can change its rules; administrators do not get them through their role, because a rule that forwards is reading the mail.
- **Mail transfer log** (`MailTransfer`, page `/Admin/Transfers`, permission `logs.view`): one line per message that comes in, goes out or moves between mailboxes, with direction (inbound / outbound / internal), channel (SMTP server, mail program, smart host, web client, provider account, rule, system) and status. Writers: `MailDelivery.DeliverAsync` when `DeliverySource.Channel` is set (SMTP port 25, provider sync, the local part of a submission, rule forwards, bounces), `OutboundQueue.EnqueueAsync` (the outgoing line, `Queued`, with its `TransferOrigin`) and `OutboundDelivery` (updates that same line: delivered / deferred / failed, attempts). `TransferLog` uses a scope of its own like `ActivityLogger` and never throws. `Retention.TransferLogDays` (default 30, 0 = no log, pruned by `MaintenanceService`) and `Retention.TransferLogSubjects` (off: no subjects). Rejections inside the SMTP dialogue (relay denied, unknown recipient) are *not* lines of this log: they stay in the activity log, where they cannot drown it in port-25 noise.

- **"Synchronise now" for users** (account menu in `_Layout`, `app.js` → `POST /api/mail/sync`): `UserSyncService` finds the connected accounts that feed the user's mailboxes (target mailbox, own address, catch-all domain, or delivered there before; send-only, disabled and foreign-tenant accounts are left out) and runs them with `MailSyncTrigger.SyncNowAsync`, four at a time, waiting up to 25 s: runs that take longer go on in the background (they belong to the server, not to the request). A custom folder is dragged with `text/x-matmail-folder` onto another folder (becomes its subfolder) or onto the **heading of its mailbox** (`makeRootTarget`: top level). `endRowDrag`/`dragend` always clear the highlights. The heading (`.folder-group__head`, also shown for a single mailbox) has a **gear** at its right end (`mat-nav__group-action` of the toolkit, SHELL-02, always visible; there is no "New folder" entry below the folders any more) and the right button → `mailboxMenu` (*New folder* for those who manage the mailbox, not for *Unassigned*; *Info…*). *Info…* (`showMailboxInfo`, `App.infoDialog`, `GET /api/mail/mailboxes/{id}/info`, needs Read access) shows type, owner, addresses, the user's access and the storage (bar, biggest folders).
- **Storage per mailbox and its limit** (`MailboxUsageService`, `MailboxQuotaService`; `Mailbox.QuotaBytes`, null = no limit, set in gigabytes on the admin page of the mailbox; migration `AddMailboxQuota`). `MailboxUsageService` sums `MailMessage.SizeBytes` (the complete raw messages, **Trash included**: deleting only moves into the trash, emptying it frees the room – the info dialog says so; live-access stand-ins count as `RemoteBytes`, not as space used). **Full means `LocalBytes >= QuotaBytes`**; one message may take a mailbox over its limit (the rule looks at what is there). What a full mailbox refuses – always before anything is stored: `MailDelivery.DeliverAsync` throws `MailboxFullException` **for the whole message** when any target mailbox is full (all or nothing: a second try must not deliver twice to the others; stand-ins of live access are never refused); the SMTP server answers `452 4.2.2` at RCPT TO (`SmtpPolicy.CheckRecipientAsync`, so the others still get it) and again at the end of DATA when a mailbox filled up meanwhile (the sender repeats the whole message); `MailSubmission` refuses a message with a full local recipient as a whole (`SubmissionResult.Temporary`, `Rejected` = the addresses; the SMTP server answers 452, `ComposeService` names the addresses for the web client); the provider sync ends the run (`MailboxFullException` is no per-message problem in `SyncImporter.IsMessageProblem`: nothing is counted towards giving up, the mail stays at the provider, delete-after-download deletes only what was stored; unclaimed mail whose fallback mailbox is full waits in *Unassigned*); IMAP `APPEND`, `COPY` and a `MOVE` into another mailbox answer `NO [OVERQUOTA]` (RFC 5530; a `COPY` into the trash of the *same* mailbox is allowed – that is how a mail program without MOVE deletes: copy to the trash, mark as deleted, expunge); the web client's move/import into a full mailbox (`MailApi.MoveMessages`, `ImportPreview`) and *Unassigned → mailbox* (`Assign`) are refused; a forwarding rule skips a full target with a warning in the activity log. What always works, so that the owner can make room: deleting, moving inside the mailbox, and what the owner writes through the web client (drafts, the copy in *Sent*). The bars (info dialog, admin pages; **not in the sidebar**: the folders are all it shows) agree: `warn` from 75 %, `high` from 90 %, `full` when reached, 100 % only when reached (`Fmt.Percent`/`Fmt.UsageState` and `usageLevel` in `mail-ui.js` – keep them equal). Shown in the admin list (sortable, with a bar), on the mailbox page (per folder) and in the info dialog of the web client.
