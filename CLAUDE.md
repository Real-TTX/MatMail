# CLAUDE.md

Guidance for working in this repository. Keep it in sync with the code: update it whenever architecture, persistence, interfaces or major data flow change.

## What MatMail is

A small self-hosted mail **gateway with a built-in web mail client** (think "tiny Exchange"). Mail accounts of external providers (Strato, Netcup, …) are connected once; users then work with the gateway's own credentials in the web client, in Outlook/Thunderbird (IMAP + SMTP of the gateway) or send through it as a smart host. A hoster can give customers their own **tenant**; the provider's real credentials never leave the server, and a provider move only changes one record.

Stack: ASP.NET Core on **.NET 10**, C#, **Razor Pages** (no Blazor/SPA framework) + TagHelper controls, EF Core + **PostgreSQL**, MailKit/MimeKit, Docker-first. Web port **9933**.

## Build / run / test

- **Build:** `dotnet build MatMail.slnx` (note: `.slnx`). SDK 10 (see `global.json`). The build is expected to end with 0 warnings.
- **Run / test the app: always rebuild the container and redeploy the stack** (project rule): `./scripts/redeploy.ps1` (`-Fresh` also wipes the volumes → the setup page appears again). Dev stack: `docker-compose.dev.yml` → http://localhost:9933, plain HTTP; mail on host ports 2525/2587/2465/2143/2993; PostgreSQL on 15432.
- **Release stack:** `docker-compose.yml` (image `ghcr.io/real-ttx/matmail`), plain HTTP on 9933 (made to run behind a reverse proxy that terminates TLS; `Server.WebHttps` is off by default, the mail servers use the certificate anyway), standard mail ports. As simple as it gets and the same file as in the README: no variables for the app, no health check, no `sysctls`, one volume for `/data` and one for PostgreSQL (its `POSTGRES_PASSWORD` equals the default of `MATMAIL__Database__Password`). That works because the app waits for PostgreSQL and creates its database itself (`StartupInitializer`); keep it that way, do not grow the file.
- **Unit/integration tests:** `dotnet test MatMail.slnx`. Tests that need PostgreSQL read `MATMAIL_TEST_DB` (an admin connection string, e.g. `Host=localhost;Port=15432;Database=postgres;Username=postgres;Password=matmail`, with the dev stack up; every test class creates and drops its own database) and are skipped without it. Tests against a real provider read `MATMAIL_TEST_IMAP` (`localhost:31143;pop3=localhost:31110;smtp=localhost:31025;api=localhost:31080`, a GreenMail container – see `tests/MatMail.Tests/Support/TestProvider.cs`; the CI starts one). A shortened value silently points the REST API at the wrong port and fails the provider tests.
- **Migrations:** `dotnet ef migrations add <Name> --project src/MatMail/MatMail.csproj --output-dir Migrations` (local tool, `dotnet tool restore`). They are applied automatically at start-up. A new `bool` column needs `HasDefaultValue(…)` in the model, otherwise EF adds it with `false` for existing rows.
- **Translations:** UI text is English in the source (`L["…"]`), German in `src/MatMail/Resources/SharedResource.de.resx` (English text = key). `node tools/i18n.mjs check` lists missing keys, `add patch.json` merges `{ "English": "Deutsch" }`, `prune` drops unused ones. Keep it complete before committing UI changes. English is the default language.
- **Screenshots** for the README: Playwright + Edge headless against a demo instance (the embedded browser pane does not render frames here); pictures live in `docs/images/`, demo data only. 1360 px wide at device scale factor 2 (mail pictures 860 px high, administration and account pages 1000 px so that the whole navigation fits, phone 390×844). The README follows the layout of MatFile's: logo and tagline, a hero picture, *What this is about*, *At a glance*, one section with a short caption per picture or row of pictures, then quick start, status, development.

## Rules from the project brief (do not drift)

- **Git:** branches `main` (release) and `dev` (development); work on `dev`. Commit under the user's own name. **Never add Claude/Anthropic as author or co-author** (no `Co-Authored-By`, no "Generated with" line). Do not push unless asked.
- **Versioning** (`Directory.Build.props`, channels): release `<major>.<minor>.<build>-<date>` (main), nightly `nightly-<build>-<date>` (dev), local `local-<date>`. The CI (`.github/workflows/docker.yml`) builds, tests and pushes the image to GHCR.
- **UI:** CRUD = list page + separate edit/create page. Every list has the **toolbar above** (search, filters, sort), list actions **below, left aligned** (destructive ones with distance), **pagination directly under the table** and nothing else. Form buttons in one row, positive → negative: `Save`, `Back`, spacer, `Delete`. Icons where they help. **One code base per control** (`src/MatMail/Controls`): table, pagination, toolbar, form, field (incl. the rich text editor), tabs, dialog, picker, buttons; several of the same control may share a page. **Mobile first-class:** dialogs and custom dropdowns become full-screen sheets on phones. The mail client looks like a modern client (Gmail). Dependent form fields are shown only when needed (`show-when-field`).
- **Code:** little nesting, several related business functions may live in one class, readable names (Microsoft C# guidelines). No repository layers.
- **Database:** PostgreSQL for logic and mail, JSON (`/data/config/app.json`) for configuration. Tables are **PascalCase** (singular, = entity name), primary key always **`Id` BIGINT**, every row has `CreateDate`, `CreateUserId`, `UpdateDate`, `UpdateUserId` (filled by `MatMailDbContext.SaveChanges`). Tables whose key acts as a security token carry a `Token` (e.g. `UserSession`: `Id` + `Token` uuid).
- **Sessions** are rows in `UserSession` (cookie carries only the token) → they survive container restarts; data-protection keys live in `/data/keys`.

## Architecture in short

Single web project `src/MatMail` (+ `tests/MatMail.Tests`).

- `Data/` – entities (`Entities/*.cs`), enums (stored as text), `MatMailDbContext` (audit columns, tenant guard, **global tenant query filter** driven by `CurrentUser.TenantId`; use `IgnoreQueryFilters()` deliberately), migrations.
- `Services/` – accounts and the application around them: `SignInService` (credentials, sessions, claims, throttling), `SessionCookieEvents` + `SessionCache` (the cookie is validated against the DB, 15 s cache), `CurrentUser` (web principal or an explicit actor for background/IMAP/SMTP: `RunAs…`), `TwoFactorService` / `TwoFactorPolicy` / `AppPasswordService` / `TwoFactorTicket` / `TwoFactorSetupMiddleware` / `Totp` (second factor, see below), `TenantService`, `UserService`, `MailboxService`, `Permissions` (role catalogue), `BrandingService`, `ThemeService` + `Fmt` (look and time zone of the user), `CertificateProvider` (PFX/PEM/self-signed, hot reload), `ProviderConnector`, `SecretProtector`, `ActivityLogger` (the operational log) and `TransferLog` (the mail transfer log, see below).
- `Push/` – notifications (Web Push): `PushKeys` (the server's VAPID key pair, made on first use in `config/push-keys.json`), `WebPushEncryption` (RFC 8291, tested byte for byte against the RFC's example), `WebPushClient` (`IPushSender`: signs and posts; only connects to public addresses), `PushPlanner` (who is told what: owner of the mailbox, others who may read it when the device asked for that; unread mail in inboxes; several at once = one notification), `PushNotifier` (hosted service: listens to `MailEventHub`, collects for two seconds, sends, keeps `PushSubscription` rows clean), `PushService` (devices of a user). Tests: `FakePushSender` stands in for the push services (`PushDatabaseTests`); the encryption is checked against the RFC's example (`WebPushEncryptionTests`).
- `MailSync/` – pulls mail from the provider accounts (IMAP incl. IDLE/flag sync, POP3), routes it through `MailDelivery`, keeps or deletes on the server per account; `LiveAccess` serves bodies that stay on the provider; `UserSyncService` is "Synchronise now" for ordinary users (see below).
- `MailServer/Imap`, `MailServer/Smtp` – the gateway's own servers (hand-written IMAP4rev1 on 143/993 and SMTP: relay 25, submission 587, implicit TLS 465). Sign-in per address or login name, throttled per (client, login); sessions re-check the user. `MailServer/Outbound` – the outgoing queue worker (provider account or direct delivery with MX lookup, retries, bounces).
- `Messaging/` – the core: `MailStore` (raw message + parsed metadata, folders), `FolderService` (the folder tree), `MailboxUsageService` (storage per mailbox and folder), `MailDelivery` (recipient → mailbox, catch-all, *Unassigned*; runs the mailbox rules and writes the transfer log), `MailRuleEngine` (mailbox rules, forwarding), `MailSubmission` (everything that leaves: **template → server signature → footers**, then local delivery or the queue), `SendRouting`, `RelayPolicy` (smart-host rules), `SignatureService`, `TemplateService`, `InlinePictures` (data: pictures become `cid:` parts), `MessageContent` (signed/encrypted mail is never changed), `MailBodyRenderer` (sanitised HTML document for the reader), `ComposeService`, `MailAccessService` (own and delegated mailboxes), `MailQuery` (the search language, see below), `MailEventHub` (push to the web client).
- `Api/MailApi.cs` – JSON API of the web client (`/api/mail/...`). The client is plain JS: `wwwroot/js/mail-core.js`, `mail-ui.js`, `mail-compose.js`, `mail-viewer.js`, `mail-search.js` (the advanced search panel). `GET /messages/ids` lists all ids a list request matches (at most `MailApi.MaxBulk`, newest first) for the bulk actions of "select all that match".
- `Configuration/AppConfig.cs` – JSON config + `MATMAIL__Section__Key` environment overrides (sections Database, Display, Server, Tls, Smtp, Imap, Sync, Queue, Retention).
- `Controls/` – TagHelpers (`mm-…`) and the SVG icon sprite (`Icons.cs`). `mm-field kind="richtext"` is the rich text editor (`wwwroot/js/rte.js` starts itself on `textarea[data-rich-text]`).
- `Pages/` – Razor Pages: `Account/` (login, setup, profile, appearance, mail program settings…), `Admin/` (dashboard, tenants, users, roles, mailboxes, domains, accounts, signatures, templates, relay, queue, branding, logs, settings), `Mail/` (web client), `Shared/` layouts.
- `wwwroot/` – `css/app.css` (tokens, shell), `components.css` (controls), `mail.css`; `js/app.js` (control behaviour), `picker.js`, `rte.js`.

Multi-tenancy: every tenant-owned entity implements `ITenantEntity`; system administrators (`User.IsSystemAdmin`) can switch tenant (stored on the `UserSession`). Permissions are role-based (`Role.Permissions`, catalogue in `Permissions.cs`); access to *another person's mailbox* is delegated separately (`MailboxPermission`), so admins do not automatically read mail. A user belongs to one tenant; addresses are unique across the server, so mail between tenants is local mail (delivery runs as the system).

## Things that are easy to get wrong

- **Signatures, footers and templates** are HTML with `{{Placeholders}}` (`SignatureContext`); the HTML is cleaned when saved (`SignatureService.SanitizeTemplate`, placeholders survive in attributes) and again when rendered. A line whose placeholders are all empty is dropped. `Signature.AddOnServer` appends a signature to messages of mail programs/smart hosts that carry none (marker class `mm-signature`); footers go on every message. `MailTemplate` puts a message into an HTML frame (`{{Body}}`), chosen by scope, source (`SubmissionSource`: web, mail program, smart host) and optionally a smart-host rule.
- **HTML that goes into the page itself** (a signature or the quoted original in the compose window, a draft, the rich text editor of the admin pages) is cleaned by `EditorHtml`, not by a plain `HtmlSanitizer`: the defaults let a `position: fixed` block with a form through, which is a fake sign-in over the whole window. No forms and controls, no positioning, no `name`/`accesskey`/`tabindex` attributes. Use it for anything that is assigned to `innerHTML` of the live page; the reader's sandboxed frame is the other way to show foreign HTML.
- **What the pipeline may touch of a message:** only the text parts that are the body (`MessageContent.BodyParts`: no attachments, no part that names a file), footers and signatures after the *last* part of each kind, a template only when there is exactly one text of each kind. Signed, encrypted and inline-PGP messages (`MessageContent.IsProtected`) are never changed. After the text of a part is replaced, `MessageContent.SetText` prepares the transfer encoding again (an old "7bit" label would stay on 8-bit bytes).
- **The app around the pages** (PWA): `wwwroot/sw.js` (registered as `/sw.js?v=<version>` by `wwwroot/js/pwa.js`, so a release is a new worker and the old caches go) keeps styles, scripts and icons (cache first), the last `/Mail` page and `/api/mail/bootstrap` (network first, only a real page, never the redirect to the sign-in page), shows push notifications and opens the message on a tap; nothing else is intercepted. The manifest is `GET /manifest.webmanifest` (`PwaManifest`; the link carries the cookies, so name and colours are the tenant's and the user's). **iOS**: `apple-mobile-web-app-status-bar-style` is `default` on purpose (`black-translucent` leaves a dead strip at the bottom on iPhones with a Dynamic Island and white text on a light header – learned in MatGate); the tags are read when the app is put on the home screen. `display` is `standalone`, not `fullscreen` (iOS cannot, and letterboxes). The bar colour is the header colour (`--color-bg`) and follows every theme change (`window.matmailBar` in `_ThemeHead`, called by `app.js`). Zoom is off three ways: the viewport tag, `touch-action: pan-x pan-y` (also in the reader's frame) and the `gesturestart` events (iPhones ignore the tag; the frame's document needs its own listener); fields are at least 16px on touch devices so that iOS does not zoom into them; after the keyboard closes iOS leaves the app panned up, `pwa.js` scrolls it back. Signing out forgets the pages cache and unsubscribes the device.
- **Offline** (`wwwroot/js/mail-outbox.js`): a message that cannot go out (offline, or the request failed without an answer) is kept in IndexedDB (`matmail` / `outbox`, per user id) as "send" or – when a window is closed offline – "draft", with its files (Blobs) and the names of the attachments already on the server. `flush` (on `online`, at start, every 30 s while something waits) uploads the files, sends, removes; a refusal by the server stays with its reason, a lost connection stops the run. An answer with a status is the server; an error without `status` is a lost connection (`isNetworkError`). There is no Background Sync: it goes out while the app is open.
- **Notifications**: `/api/mail/push/*` (config, status, subscribe, unsubscribe, test) and `/api/mail/csrf` (a fresh token for what runs without the page); the page `/Account/App` (`account-app.js`) is the switch and the list of devices. Endpoints come from the browser, so `WebPushClient` only connects to public addresses (no loopback/private/link-local: otherwise a user could make the server post into its own network). `Push.Enabled` / `Push.Contact` (`MATMAIL__Push__…`) in the configuration.
- **Printing** cannot happen in the reader's frame: the browser ignores `print()` of a sandboxed frame without `allow-modals` (and phones do not print frames at all). `GET /api/mail/messages/{id}/print` renders header and body as one document (`MailBodyRenderer.BuildPrintDocument`) with a single script found by its CSP nonce that opens the print dialog; the client opens it in a new window (`printMessage`). The share sheet entry (`navigator.share`, `.eml` as file) appears on touch devices only.
- **The reader** shows foreign HTML in a sandboxed iframe without scripts; the parent page (`mail-viewer.js`) adjusts the same-origin iframe document (fit to width, quote folding). Remote content is blocked until the user allows it.
- **Search** (`MailQuery`): the text becomes a tree (`AndNode`/`OrNode`/`NotNode`/`TermNode`) and from that an EF expression, no fulltext engine. Operators `from to subject has:attachment is:unread|read|starred|answered|draft in before after older_than newer_than larger smaller` and their German names (`von an betreff hat ist ordner vor nach älter_als neuer_als größer kleiner`), `OR`/`ODER`/`|` (binds weaker than the blank between terms: `a OR b c` is `a OR (b c)`; brackets make it explicit), `-`, `( )`, `{a b}` (either), `key:(a OR b)`, quoted phrases. What is no operator, or has no sensible value (`before:soon`), stays a plain word: a typo is never an error. Scope: the folder of the list, else the whole mailbox without Trash and Junk; a positive `in:` (a system folder in either language, `anywhere`, or the name/path of a folder – `ResolveFoldersAsync` looks those up) beats both. The web client starts every search mailbox-wide (the folder leaves the address). A new operator touches `MailQuery` (`Operators`/`GermanKeys`, `Keyed`, `Term`), `MailQueryTests`, `mail-search.js` (the panel writes and reads the same text: `KEYS`, `absorb`, `composeQuery`; text it cannot place stays in its "has the words" field, so nothing is lost or reordered across an `OR`) and the README.
- **"Select all that match"** (Gmail style): `S.allMatching` in `mail-ui.js` is set when the whole page is selected and the user takes the offer under the toolbar; the actions then go through `actSelected`, which fetches `/messages/ids` for the same mailbox/folder/query, asks once (not for read/unread/star) and calls `act(…, { origin })`. `postIds` sends the ids in chunks of 500 (the server takes at most 1000 per call) and adds the answers up; undo uses the same path. Anything that changes the list or the selection by hand resets the mode.
- **Display settings** (theme, accent, text size, density, previews, time zone, language) are columns of `User`, travel in claims (`SessionSnapshot` → `AppClaims`) and end up as `data-*` attributes of `<html>`; CSS and `Fmt` react to them.
- **Two-factor authentication** (TOTP, RFC 6238, no library; QR code drawn on the server by QRCoder). Web sign-in: password → `SignInService.ValidateCredentialsAsync` returns `SecondFactorPending` → the Login page issues the `MatMail.TwoFactor` ticket cookie (data-protected, 5 minutes, HttpOnly, SameSite Strict, path `/Account`; not a session) → `/Account/TwoFactor` → only then the session. **Nothing but the Login and TwoFactor pages decides that the second step happened** (`SignInAsync` does not check): any new way to create a session has to enforce it. Wrong codes count against the same atomic lockout as wrong passwords; a code works once (`UserTotp.LastUsedStep`). IMAP and SMTP cannot ask for a code: `SignInPurpose.Protocol` accepts **app passwords** (24 characters, PBKDF2, shown once, `AppPassword`), and the account password only while 2FA is neither on nor required; app passwords never work on the web. The tenant policy (`Tenant.TwoFactorMode`: optional, administrators, everyone) and the role flag (`Role.RequiresTwoFactor`) make it mandatory; someone bound to it but not enrolled is held on `/Account/Security` by `TwoFactorSetupMiddleware` (a fixed list of open addresses, `/api` answers 403). Permission `security.manage`. Lost phone and no recovery codes: an administrator resets it (user page), or `DELETE FROM "UserTotp" WHERE "UserId" = …` (cascades to the recovery codes). Test helpers: `TestClock`, `TwoFactorTestSupport`.
- **Mailbox rules** (`MailRule` with `MailRuleCondition` and `MailRuleAction`; pages `/Account/Rules` and `Rules/Edit`, script `rules.js`). The engine decides **before the message is stored** (`MailDelivery.StoreAsync`): the message arrives read, starred, labelled and in its folder, so nothing flickers through the inbox and no notification is sent for it. Rules run only for mail that is routed into an inbox: not for the *Unassigned* bucket, not for backup/migration copies, not for `DeliverToMailboxAsync`. A problem of a rule never costs the message (the delivery logs it and stores without rules). Conditions on what is not there (the text of a live-access stand-in, a missing header) never match, not even negative ones; a rule without conditions or with an empty text matches nothing. **Forwarding is a redirect**: the original bytes with `Resent-*` headers in front and, as envelope sender, an address of the mailbox (the provider accepts that), through `MailDelivery` (local) or the outgoing queue. It happens **after** the copy is stored, so a loop of forwarding rules meets its own copy (Message-ID de-duplication) and ends; `X-MatMail-Forward-Hops` (limit 5) is the second guard. A message a rule changed on arrival gets its `UpdateDate` bumped after the provider record is written (`ImportResult.RuleChangedFlags`), otherwise the flag comparison would take the provider's flags and undo the rule; a rule that deletes a message counts as "dealt with" for *delete after download*. Deleting a folder a rule moves into keeps the action with `FolderId = null` (it then does nothing). Only people with **Manage** access to a mailbox (the owner, or delegated) can change its rules; administrators do not get them through their role, because a rule that forwards is reading the mail.
- **Mail transfer log** (`MailTransfer`, page `/Admin/Transfers`, permission `logs.view`): one line per message that comes in, goes out or moves between mailboxes, with direction (inbound / outbound / internal), channel (SMTP server, mail program, smart host, web client, provider account, rule, system) and status. Writers: `MailDelivery.DeliverAsync` when `DeliverySource.Channel` is set (SMTP port 25, provider sync, the local part of a submission, rule forwards, bounces), `OutboundQueue.EnqueueAsync` (the outgoing line, `Queued`, with its `TransferOrigin`) and `OutboundDelivery` (updates that same line: delivered / deferred / failed, attempts). `TransferLog` uses a scope of its own like `ActivityLogger` and never throws. `Retention.TransferLogDays` (default 30, 0 = no log, pruned by `MaintenanceService`) and `Retention.TransferLogSubjects` (off: no subjects). Rejections inside the SMTP dialogue (relay denied, unknown recipient) are *not* lines of this log: they stay in the activity log, where they cannot drown it in port-25 noise.
- **Folder tree**: `FolderService.ListAsync` returns the folders depth first (a folder is followed by its subfolders, `Arrange`), because ordering by the kind of a folder alone would put a subfolder of the inbox after the trash. Subfolders of any folder are possible (also below system folders); `MoveAsync` (web client menu and drag & drop) refuses a move into itself or a descendant, a taken name, a reserved top-level name and more than `MaxDepth` levels. IMAP needs nothing special: names are built from the parent chain. The web client folds subfolders per browser (`matmail-fold-<id>` in local storage) and shows the unread count of a folded subtree on the folder.
- **"Synchronise now" for users** (account menu in `_Layout`, `app.js` → `POST /api/mail/sync`): `UserSyncService` finds the connected accounts that feed the user's mailboxes (target mailbox, own address, catch-all domain, or delivered there before; send-only, disabled and foreign-tenant accounts are left out) and runs them with `MailSyncTrigger.SyncNowAsync`, four at a time, waiting up to 25 s: runs that take longer go on in the background (they belong to the server, not to the request). The answer says how many accounts were fetched, how many messages came in and how many failed; only people with `accounts.manage` get the reason of a failure (it names servers).
- **Storage per mailbox**: `MailboxUsageService` sums `MailMessage.SizeBytes` (the complete raw messages). Live-access stand-ins count as `RemoteBytes` (they stay at the provider), not as space used. Shown in the admin list (sortable), on the mailbox page (per folder) and in the web client (below the folders). There is no quota yet.
- **Forms posting to an explicit `action`** need `@Html.AntiForgeryToken()`.
