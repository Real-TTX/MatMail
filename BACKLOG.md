## Notes on the design

- **Member of several tenants** (open, needs a decision of the owner). *What was asked:* a tenant switcher in the web client for somebody who has access to mail in another tenant. *Where the model stands:* a user belongs to one tenant (`User.TenantId`), every query runs inside the tenant of the session (global query filter) and `SaveChanges` refuses to write across tenants; only system administrators switch (`UserSession.TenantId`). *Three ways.* **(1) Delegation across tenants:** a mailbox of tenant B is delegated to a user of tenant A, who stays a member of A and sees the mailbox in their own list like any shared mailbox (IMAP lists it too); nothing to switch. The administrators of B give access by typing an address – they cannot list the users of A. It needs a carve-out in the tenant guard (a request that reads mailbox B runs with the tenant of B after the delegation has been checked; the `MailboxPermission` rows of a user are read ignoring the filter) and is the smallest change that answers the wish. **(2) Memberships:** `UserTenant(user, tenant, roles)`; a user has a home tenant and further memberships with roles of their own, the session carries the active tenant (the mechanism of system administrators) and the switcher lists the memberships. One tenant at a time in the web client, and IMAP and SMTP need a rule for which tenant a login means. **(3) Linked users:** one person, several `User` rows tied together – duplicates profile, password and second factor; not recommended. *Recommendation:* (1) now, (2) only when somebody has to *administer* several tenants without being a system administrator. Whichever it is, the tenant boundary is the most dangerous place of the program: every new path across it gets tests that try to cross it without permission.
- **Directories (AD / LDAP)** (implemented). A *directory* belongs to a tenant: where it is (host, port, plain / STARTTLS / LDAPS, an account that searches), which entries are people (base, filter, login attribute), the *mapper* (which attribute fills which field of the user), who may sign in (a group, read from the person's `memberOf` or from the member list of the group, Active Directory's nested rule on request) and what a first-time user gets (roles, a mailbox). The client is Novell.Directory.Ldap.NETStandard (pure .NET, nothing native in the container; it connects to the first address only, so `LdapDirectoryClient` tries the addresses of a name one by one: IPv6 first and not served, as for `localhost`, would be "unreachable"). *The password of a person is never stored and never read:* a sign-in searches the person (the search account), then binds as that person on a connection of its own; an empty password is never sent (many servers answer a bind without a password with success). Logins are escaped as filter values (RFC 4515). A user made from a directory has a random hash nobody knows; `SignInService` asks the directory instead, for the web and, with a two-minute memory of a success, for IMAP and SMTP (mail clients sign in again for every folder). Two-factor authentication and app passwords stay MatMail's: password (directory) → code (MatMail); IMAP and SMTP take app passwords like everybody else's. Blocking is `User.DirectoryDisabledDate` (set by the comparison: gone, disabled in Active Directory through `userAccountControl`, or outside the group; open sessions end at once; the next successful sign-in or comparison clears it). A comparison that cannot reach the directory changes nothing. A login that a user has here already always belongs to that user (login names are unique across the server), and a deleted directory leaves its people as users nobody can sign in as until an administrator gives them a password. *Guessing:* every wrong password at the web client is a failed bind at the directory, which may lock the real account there; for somebody without a user here `DirectoryAttemptLimiter` stops asking about a login after five wrong passwords in 15 minutes (and about a client after 50 failures); somebody with a user is held by that user's lockout (also five). Set the lockout threshold of the directory above five. Not built: writing to the directory (no password change, no profile photos), Kerberos / NTLM single sign-on, several base DNs per connection, paged searches (a test looks at the first 1000 entries, the import page shows 200 and the search narrows them down).

- **App passwords** (implemented). As soon as a user (or the whole tenant) must use a second factor, IMAP/SMTP clients cannot do the web login. They get *app passwords*: random, shown once, named per device, revocable, usable only for IMAP and SMTP. Without this the second factor could be bypassed through IMAP. Not built: notification mails, "remember this device", WebAuthn.
- **Signature kinds.** One signature has the placement "offered in the client", "added by the server" or both. Server-added signatures only apply to messages that do not carry the marker of an already applied one (so the web client's own insertion is not doubled). Signed and encrypted messages are never changed.
- **Templates by rule** sit in the pipeline *before* the signature and the footers: `template (HTML with {{Body}}) → server signature → footers`. A template is chosen by who sends (tenant, mailbox, user), where the message comes from (web client, mail program, a given smart-host rule) and whether it has an HTML part at all.
- **Backup and restore** (implemented). *What is in a backup:* every table of schema `public` (PostgreSQL binary `COPY` in one snapshot) and every file under `/data` except the scratch folders, discovered at the time of the backup – so new tables and files are covered without a change, which is why the rule is that all persistent state lives in PostgreSQL or under `/data`. *Old backups:* the schema version is the last EF migration (a restore builds the schema of the backup and migrates forward over the loaded data, like an update), the layout of the files and of data that a migration cannot express is `DataMigrations` (numbered steps, stored in `SystemSetting` and in the manifest), and the backup format has its own number; a program never touches data of a newer version. *Restore* is one database transaction plus a rename of staged files; a running program only leaves a request and stops (`restart: unless-stopped` starts it again), the start-up restores behind a progress page. *Old backups* are guarded by two real files of the first version (`GoldenBackupTests`: every table has rows, so later migrations have to work on data in each) and by tests that restore a backup of every earlier schema; migrations of a release are never deleted or changed. *Measured:* a database of 1.1 GB (200 messages of 5.6 MB; the big table was cut into parts of 512, 512 and 70 MB) backed up and verified in 71 s and restored in 173 s without the memory of the process growing (it stayed at about 260 MB: tables, parts and files are streamed). Not built: resuming an interrupted upload to a share, SMB 3.1.1 (SMBLibrary offers 2.0.2 to 3.0.2; signing and AES-128-CCM encryption work), incremental or deduplicated backups (a backup is always whole), restoring a single mailbox or message.
- **Branding** is data of the tenant (display name, logo, accent colour, optional support address); the sign-in page of a tenant is reached through its name in the URL (`/t/<slug>`), the shared sign-in page stays neutral.
- **Storage limit per mailbox** (implemented). *What it is:* `Mailbox.QuotaBytes` (none by default). A mailbox is *full* when the complete messages stored in it reach the limit; what stays at the provider (live access) is not counted, **the trash is** (deleting moves a message there, emptying the trash frees the room – the info dialog points at it). *What a full mailbox refuses,* always before anything is stored: new mail from outside, from other mailboxes (web client, mail program, rules) and copies or moves into it. The SMTP server answers `452 4.2.2`, not `552`: a temporary error, so that the sender tries again instead of giving up – at RCPT TO, so that the other recipients still get the message, and again at the end of DATA for a mailbox that filled up meanwhile. A connected account ends its run and the mail stays at the provider (delete-after-download only deletes what was stored; unclaimed mail whose fallback mailbox is full waits in *Unassigned*). **A message for several recipients goes to all of them or to none**: the sender and the provider repeat a message as a whole, a partial delivery would deliver twice. IMAP answers `NO [OVERQUOTA]` (RFC 5530) to `APPEND`, `COPY` and a `MOVE` into another mailbox – an `APPEND` is an upload of any size, so a limit that it could pass would be none; only a `COPY` into the trash of the same mailbox is let through, because that is how a mail program without MOVE deletes (Dovecot has a grace for the same reason). *What still works:* deleting, moving inside the mailbox, and what the owner writes through the web client (drafts, the copy in *Sent*), so that the owner can always make room. *Why the rule looks at what is there and not at the size of what comes:* at RCPT TO the size is not known, and one message may take a mailbox over its limit. Not built: the IMAP QUOTA extension, a mail to the owner at 90 %, a default per tenant or role, a hard cap that also stops the owner's own writes.
